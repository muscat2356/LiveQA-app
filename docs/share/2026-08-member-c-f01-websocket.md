## 1. 今回の学習目的

今回の学習では、WebSocketとSTOMPの基本を理解し、live-qa-appでリアルタイム通信を実現する仕組みを学ぶことを目的とする。

live-qa-appは、セミナーや勉強会で利用するライブQ&Aアプリである。

参加者が質問を投稿すると、その質問は投稿者だけではなく、同じイベントへ参加している全員の画面へすぐに反映される必要がある。

同様に、次の変更もリアルタイムに反映したい。

- 新しい質問が投稿された
- 質問へのいいね数が変わった
- 主催者が質問を回答済みに変更した
- 主催者が質問を非表示にした
- MVP-BではPollが開始・更新・終了した

これらを実現するため、通常のREST APIに加えて、WebSocket / STOMPを利用する。

---

## 2. live-qa-appでリアルタイム通信が必要な理由

通常のWebアプリでは、利用者が操作したときにサーバーへリクエストを送り、レスポンスを受け取る。

しかし、live-qa-appでは、自分以外の参加者が行った操作も、自分の画面へすぐに反映する必要がある。

例えば、参加者Aが質問を投稿したとする。

```text
参加者A
「Docker ComposeとDockerfileの違いは何ですか？」
        │
        ▼
質問を投稿
```

このとき、参加者Bや主催者は何も操作していない。

通常のHTTP通信では、参加者Bや主催者が新しくリクエストを送らない限り、質問が投稿されたことを知ることができない。

```text
参加者Aが質問を投稿
        │
        ▼
サーバーのDBへ保存
        │
        ▼
参加者B・主催者の画面は更新されない
```

WebSocketを利用すると、サーバーから接続中の利用者へ更新内容を送信できる。

```text
参加者Aが質問を投稿
        │
        ▼
REST APIでDBへ保存
        │
        ▼
WebSocketで接続中の利用者へ配信
        │
        ▼
参加者B・主催者の画面も更新
```

このように、利用者が画面を更新しなくても、サーバーから接続中の利用者へ変更内容を通知できることが、WebSocketを利用する目的である。

---

## 3. HTTP通信の基本

通常のWebアプリでは、利用者が操作したときに、ブラウザからサーバーへHTTPリクエストを送り、サーバーからブラウザへHTTPレスポンスが返される。

例えば、利用者が質問一覧を表示するときの流れは次のとおりである。

```text
ブラウザ
      │ HTTPリクエスト
      ▼
サーバー
      │ 質問一覧を取得
      ▼
ブラウザ
（HTTPレスポンス）
```

HTTP通信は、リクエストとレスポンスが完了すると通信も終了する。

そのため、参加者Aが質問を投稿し、サーバーがその内容をDBへ保存しても、参加者Bや主催者の画面は自動では更新されない。

---

## 4. ポーリングによる更新

ポーリングとは、一定時間ごとにブラウザからサーバーへHTTPリクエストを送り、新しい情報があるか確認する方法である。

例えば、5秒ごとに質問一覧を取得する場合は、次のようになる。

```text
ブラウザ
      │ HTTPリクエスト
      ▼
サーバー
      │ HTTPレスポンス
      ▼
ブラウザ

（5秒後）

ブラウザ
      │ HTTPリクエスト
      ▼
サーバー
      │ HTTPレスポンス
      ▼
ブラウザ

（5秒後）

……
```

ポーリングでは、新しい質問が投稿されていなくても、一定時間ごとにHTTP通信が発生する。

また、参加者Aが質問を投稿しても、参加者Bや主催者の画面へ反映されるのは次のポーリングが実行された後になる。

電話に例えると、HTTP通信とポーリングの違いは次のようになる。

```text
【HTTP】

電話

「質問一覧をください。」

「はい。」

電話を切る
```

```text
【ポーリング】

5秒ごとに電話をかける

「新しい質問はありますか？」

「ありません。」

電話を切る

      ↓

5秒後

「新しい質問はありますか？」

「ありません。」

電話を切る
```

このように、ポーリングはHTTP通信を繰り返すことで画面を更新する仕組みである。

しかし、更新がなくても通信が発生することや、次のポーリングまで画面へ反映されないことが課題である。

---

## 5. WebSocketとは

WebSocketは、ブラウザとサーバーが接続を維持したまま通信できる仕組みである。

HTTP通信では、リクエストとレスポンスが完了すると通信も終了する。

一方、WebSocketでは、一度接続すると通信を維持したままになる。

```text
ブラウザ
      │
      │ WebSocket接続（接続を維持）
      │
サーバー
```

この接続を利用して、

- ブラウザからサーバーへデータを送信できる
- サーバーからブラウザへデータを送信できる

そのため、参加者Aが質問を投稿すると、サーバーは接続中の参加者Bや主催者へ新しい質問をすぐに配信できる。

電話に例えると、WebSocketは電話をつないだまま会話するような仕組みである。

```text
【WebSocket】

電話をつなぐ

────────────

・・・

・・・

・・・

参加者Aが質問を投稿

↓

サーバー
「新しい質問が投稿されました。」

↓

参加者B・主催者
「画面を更新します。」
```

WebSocketは接続を維持しているが、常にデータを送受信し続けているわけではない。

データは、更新が発生したときだけ送受信される。

そのため、更新がなくても一定時間ごとにHTTP通信を行うポーリングよりも、効率よくリアルタイム通信を実現できる。

---

## 6. HTTPとWebSocketの違い

HTTPとWebSocketの違いをまとめると、次のようになる。

| 項目 | HTTP | WebSocket |
|------|------|-----------|
| 接続方法 | リクエストごとに通信を開始する | 最初に接続し、その後は接続を維持する |
| 接続状態 | 通信が完了すると接続が終了する | 接続を維持したまま通信する |
| サーバーからの送信 | ブラウザからリクエストがあったときだけレスポンスを返す | 接続中のブラウザへ必要なタイミングでデータを送信できる |

live-qa-appでは、WebSocketを利用することで、参加者Aが質問を投稿すると、サーバーは接続中の参加者へ更新内容をリアルタイムに配信できる。

---

## 7. WebSocket接続の流れ

WebSocket通信を行うためには、最初にブラウザとサーバーがWebSocket接続を確立する必要がある。

接続の流れは次のとおりである。

```text
① ブラウザがサーバーへ
   WebSocket接続を要求する
                │
                ▼
② サーバーが
   WebSocket接続要求を受け入れる
                │
                ▼
③ ブラウザとサーバーの
   WebSocket接続が確立される
                │
                ▼
④ ブラウザとサーバーが
   WebSocket通信を開始する
```

WebSocket接続が確立されると、その接続を利用してブラウザとサーバーがデータを送受信できる。

一度接続すると、ブラウザまたはサーバーが接続を切断するまで、その接続は維持される。

例えば、利用者がブラウザや画面を閉じると、WebSocket接続も切断される。

サーバーは、WebSocket接続が切断されたことを検知できる。

そのため、切断した利用者を接続中の利用者一覧から除外するなどの処理を行うことができる。

---

## 8. STOMPとは

WebSocketは、ブラウザとサーバーが通信するための仕組みである。

しかし、WebSocketだけでは、

- 誰へデータを送信するのか
- どの種類のデータを送信するのか

といったルールは決まっていない。

そこで利用するのがSTOMPである。

STOMPは、WebSocket上でデータをやり取りするためのルール（プロトコル）である。

live-qa-appでは、STOMPを利用することで、

- 質問一覧
- いいね数
- 質問ステータス

など、更新内容ごとにデータを配信できる。

---

## 9. WebSocketとSTOMPの関係

WebSocketとSTOMPの役割は次のように異なる。

| 項目 | WebSocket | STOMP |
|------|-----------|--------|
| 役割 | ブラウザとサーバーが通信する仕組み | データをやり取りするためのルール |
| 担当 | 通信路を提供する | 誰へ・何を送るかを決める |

電話に例えると、次のようになる。

```text
【WebSocket】

電話回線
└─ 相手と通話するための通信経路
```
```text
【STOMP】

会話のルール
├─ 最初に「もしもし」と伝える
├─ 用件を伝える
└─ 相手が返事をする
```

このように、

- WebSocketは、ブラウザとサーバーが通信するための経路を作る
- STOMPは、その通信経路を使ってデータをやり取りするためのルールを決める

という役割分担になっている。

live-qa-appでは、WebSocketとSTOMPを組み合わせることで、参加者ごとに必要なデータをリアルタイムに配信している。

---

## 10. Publish / Subscribeモデル

STOMPでは、Publish / Subscribeモデルを利用してデータを配信する。

役割は次の2つである。

- **Publish（送信）**：データを送信する
- **Subscribe（購読）**：データを受信できるよう待機する

live-qa-appでは、参加者や主催者のブラウザが、あらかじめ必要なデータをSubscribe（購読）して待機している。

例えば、質問一覧を配信する流れは次のとおりである。

```text
① 参加者や主催者のブラウザが
   質問一覧をSubscribe（購読）する
                │
                ▼
② サーバーが
   質問一覧をPublish（送信）する
                │
                ▼
③ Subscribe（購読）しているブラウザが
   データを受信する
```

Subscribe（購読）していないブラウザには、そのデータは配信されない。

そのため、必要な利用者だけへデータを配信できる。

## 11. live-qa-appの通信構成

live-qa-appでは、REST APIとWebSocketを役割ごとに使い分けている。

質問を投稿する流れは次のとおりである。

```text
① 参加者Aが質問を投稿する
                │
                ▼
② ブラウザがREST APIで
   サーバーへリクエストを送信する
                │
                ▼
③ サーバーがDBへ質問を保存する
                │
                ▼
④ サーバーがWebSocketで
   接続中の参加者へデータを配信する
                │
                ▼
⑤ 参加者B・主催者の画面が更新される
```

REST APIは、質問を登録するために利用する。

WebSocketは、登録された質問を接続中の参加者へリアルタイムに通知するために利用する。

このように、それぞれの役割を分けることで、効率よくリアルタイム通信を実現している。

---

## 12. RESTとWebSocketの役割分担

live-qa-appでは、REST APIとWebSocketを目的に応じて使い分けている。

それぞれの役割は次のとおりである。

| 処理 | 利用する仕組み | 理由 |
|------|----------------|------|
| 質問を投稿する | REST API | サーバーへデータを登録するため |
| いいねを登録する | REST API | サーバーへデータを登録するため |
| 質問ステータスを変更する | REST API | サーバーへデータを更新するため |
| 新しい質問を参加者へ通知する | WebSocket | 接続中の参加者へリアルタイムに配信するため |
| いいね数の変更を通知する | WebSocket | 接続中の参加者へリアルタイムに配信するため |
| 質問ステータスの変更を通知する | WebSocket | 接続中の参加者へリアルタイムに配信するため |

live-qa-appでは、

- 質問投稿
- いいね
- 質問ステータス変更

のいずれも、

**「REST APIでDBを登録・更新し、その後WebSocketで更新内容を配信する」**

という共通の流れで処理を行う。

このように、REST APIはデータを登録・更新する役割、WebSocketは変更内容をリアルタイムに通知する役割を担当している。

## 13. STOMPのチャンネル

live-qa-appでは、質問一覧やいいね数など、さまざまな更新をリアルタイムに画面へ反映する。

しかし、質問一覧の更新といいね数の更新を同じ送り先へ配信すると、画面は受信した更新内容を区別できない。

そのため、更新内容ごとに送り先を分ける。

STOMPでは、この送り先を**チャンネル**と呼ぶ。

例えば、質問一覧を配信するためのチャンネルとして、次のような名前を利用する。

```text
/topic/questions
```

質問一覧画面は、このチャンネルをSubscribe（購読）して待機する。

一方、サーバーは、質問一覧が更新されると、このチャンネルへPublish（送信）する。

```text
                 購読（Subscribe）

質問一覧画面 ◀────────────────┐
                              │
                  /topic/questions
                    （チャンネル）
                              ▲
                              │
サーバー ─────────────────────┘
                   送信（Publish）
```

つまり、

- **質問一覧画面**は、`/topic/questions`をSubscribe（購読）し、質問一覧の更新を受信する。
- **サーバー**は、質問一覧が更新されると、`/topic/questions`へPublish（送信）する。

その結果、`/topic/questions`をSubscribe（購読）している画面だけが、質問一覧の更新をリアルタイムに受信できる。

## 14. 配信イベントの設計

チャンネルを決めたら、次は「どのような更新を配信するか」を決める必要がある。

この「○○が起きました」という出来事を表す通知を**イベント**と呼ぶ。

例えば、live-qa-appでは、次のようなイベントを配信する。

| イベント | 配信するタイミング |
|----------|------------------|
| 質問投稿 | 新しい質問が投稿されたとき |
| いいね更新 | いいね数が変更されたとき |
| 質問ステータス変更 | 主催者が質問ステータスを変更したとき |

例えば、参加者が新しい質問を投稿すると、「質問投稿イベント」が作成され、質問一覧を配信するチャンネルへ送信される。

```text
質問投稿イベント
        │
        ▼
/topic/questions（チャンネル）
        │
        ▼
質問一覧画面
```

質問一覧画面は、`/topic/questions`をSubscribe（購読）しているため、質問投稿イベントを受信すると画面を更新する。

いいね数や質問ステータス変更も同じ考え方で、それぞれ対応するイベントを対応するチャンネルへ配信する。

このように、更新内容ごとにイベントを分けることで、必要なタイミングで必要な情報だけを画面へ配信できる。

---

## 15. 配信ペイロード

イベントをチャンネルへ配信するときは、画面を更新するためのデータも一緒に送信する。

この画面を更新するためのデータを**ペイロード**と呼ぶ。

例えば、「質問投稿イベント」のペイロードは、次のようになる。

| 項目 | 内容 |
|------|------|
| id | 質問ID |
| content | 質問内容 |
| likeCount | いいね数 |
| status | 質問ステータス |

配信イメージは次のとおりである。

```text
┌────────────────────────────┐
│ 質問投稿イベント            │
│                            │
│ ペイロード                 │
│ ・id                       │
│ ・content                  │
│ ・likeCount                │
│ ・status                   │
└────────────────────────────┘
             │
             ▼
      /topic/questions（チャンネル）
             │
             ▼
         質問一覧画面
```

このように、イベントは「何が起きたか」を表し、ペイロードは「画面を更新するためのデータ」を表している。

Spring Bootでは、サーバーからチャンネルへペイロードを配信するために、`SimpMessagingTemplate`というクラスを利用する。

例えば、質問一覧を更新する場合は、次のように利用する。

```java
simpMessagingTemplate.convertAndSend(
    "/topic/questions",
    questionDto
);
```

コードの役割は次のとおりである。

| コード | 役割 |
|--------|------|
| `convertAndSend()` | 指定したチャンネルへペイロードを配信する（Springが用意しているメソッド） |
| `/topic/questions` | 配信先のチャンネル |
| `questionDto` | 配信するペイロード |

`questionDto`には、質問IDや質問内容など、画面を更新するためのデータが格納されている。

配信の流れは次のとおりである。

```text
サーバー
   │
   │ convertAndSend()
   ▼
/topic/questions（チャンネル）
   │
   ▼
質問一覧画面
（イベントを受信すると画面を更新）
```

## 16. チャンネルの購読

ブラウザは、`subscribe()`を利用してチャンネルをSubscribe（購読）する。

例えば、質問一覧を受信する場合は、次のように設定する。

```javascript
client.subscribe("/topic/questions", (message) => {
    const questionDto = JSON.parse(message.body);
});
```

コードの役割は次のとおりである。

| コード | 役割 |
|--------|------|
| `subscribe()` | チャンネルを購読する（STOMPが用意しているメソッド） |
| `/topic/questions` | 購読するチャンネル |
| `message.body` | サーバーから受信したペイロード |
| `JSON.parse()` | 受信した文字列をJavaScriptのオブジェクトへ変換する |

`subscribe()`を実行すると、ブラウザは指定したチャンネルを購読した状態になる。

サーバーからペイロードが配信されると、ブラウザはそれを受信し、画面の更新に利用する。

受信の流れは次のとおりである。

```text
サーバー
   │
   │ questionDto（ペイロード）を配信
   ▼
/topic/questions（チャンネル）
   │
   ▼
ブラウザ
（Subscribe済み）
   │
   ▼
画面を更新
```

## 17. 質問投稿から画面更新まで

ここまで説明した内容をまとめると、質問投稿から画面更新までの流れは次のようになる。

```text
参加者が質問を投稿
        │
        ▼
サーバーで質問を登録
        │
        ▼
questionDto（ペイロード）を作成
        │
        ▼
convertAndSend()で
/topic/questionsへ配信
        │
        ▼
ブラウザが
subscribe()で受信
        │
        ▼
画面を更新
```

このように、ブラウザはサーバーから配信されたペイロードを受信し、画面をリアルタイムに更新する。

そのため、利用者がブラウザを手動で更新しなくても、新しい質問を確認できる。

## 18. WebSocketハンドシェイク

WebSocketは、一度接続すると通信を維持し続ける。

しかし、最初からWebSocket通信を始めるわけではない。

最初はHTTP通信で接続を要求し、サーバーが接続を許可すると、WebSocket通信へ切り替わる。

この最初の接続確認を**WebSocketハンドシェイク**と呼ぶ。

接続の流れは次のとおりである。

```text
① 画面
      │ HTTPで接続を要求
      ▼
② サーバー
      │ 接続を許可
      ▼
③ WebSocket接続開始
      │
      ▼
リアルタイム通信
```

ハンドシェイクが完了すると、以降はHTTP通信を繰り返すことなく、同じ接続を利用してリアルタイム通信を行う。

そのため、新しい質問やいいね数の変更などを、サーバーから画面へすぐに配信できる。

## 19. 利用者の識別

live-qa-appには、**主催者**と**一般参加者**の2種類の利用者が存在する。

それぞれのできることは次のとおりである。

| 利用者 | できること |
|--------|-----------|
| 主催者 | 質問の回答済み変更、非表示、Pollの開始・終了など |
| 一般参加者 | 質問投稿、いいね、質問一覧の閲覧 |

WebSocketハンドシェイクは、最初にHTTP通信で接続を開始する。

`SESSION` Cookieとは、利用者ごとに発行されるセッション情報を保存するCookieである。

そのため、ブラウザは通常のHTTP通信と同じように、`SESSION` Cookieもサーバーへ送信する。

接続の流れは次のとおりである。

```text
画面
  │
  │ HTTPで接続要求
  │ （SESSION Cookieを送信）
  ▼
サーバー
  │
  │ SESSION Cookieを確認
  ▼
WebSocket接続開始
```

一般参加者はログイン不要である。

しかし、イベントページを開いた時点で`SESSION`が自動的に作成されるため、サーバーは一般参加者も利用者ごとに識別できる。

そのため、サーバーは`SESSION` Cookieを利用して利用者を識別し、利用者ごとに実行できる処理を制御している。

## 20. RedisとWebSocket認証

本番環境では、多くの利用者からのアクセスを処理するため、複数のサーバーで同じWebアプリケーションを動かすことがある。

このとき、**ロードバランサ**（利用者を複数のサーバーへ振り分ける仕組み）を利用する。

```text
            利用者
               │
               ▼
        ロードバランサ
   （接続先を振り分ける）
          │
      ┌───┴───┐
      ▼       ▼
 サーバーA  サーバーB
```

そのため、どのサーバーが利用者からの通信を処理するかは固定ではない。

サーバーごとに`SESSION`情報を管理していると、別のサーバーへ接続したときに利用者を識別できなくなる。

そこで、複数のサーバーから共通して利用できるセッション情報の保存先として**Redis**を利用する。

```text
      サーバーA
          │
          ├────┐
          │    │
          ▼    ▼
        Redis
          ▲    ▲
          │    │
          └────┤
      サーバーB
```

このように、`SESSION`情報をRedisで共有することで、どのサーバーへ接続しても同じ利用者として識別できる。

利用者ごとに「どの操作を許可するか」を決めることを**認可**と呼ぶ。

live-qa-appでは、利用者ごとに実行できる操作が異なる。

| 利用者 | 許可する操作 |
|--------|-------------|

| 一般参加者 | 質問投稿、いいね |

*Poll：リアルタイムに投票やアンケートを実施する機能

## 22. WebSocketConfig

ここからは、live-qa-appにおけるWebSocketの実装方法を説明する。

まず、WebSocketを利用するためには、Spring BootへWebSocketの設定を登録する必要がある。

この設定を行うクラスが**WebSocketConfig**である。

役割は次の3つである。

- WebSocketを有効化する
- 接続先（エンドポイント）を設定する
- WebSocket通信に必要な設定を行う

クラス構成は次のようになる。

```java
@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

}
```

各アノテーションの役割は次のとおりである。

| アノテーション | 役割 |
|--------------|------|
| `@Configuration` | Springの設定クラスであることを表す |
| `@EnableWebSocketMessageBroker` | WebSocketとSTOMPを有効にする |
| `WebSocketMessageBrokerConfigurer` | WebSocketの各種設定を行うためのインターフェース |

このクラスでは、このあと説明するエンドポイントやチャンネルなど、WebSocket通信に必要な設定を行う。

---

## 23. エンドポイント設定

22章で実装した`WebSocketMessageBrokerConfigurer`には、WebSocketの設定を行うためのメソッドが用意されている。

その1つが、Springが用意している`registerStompEndpoints()`である。

このメソッドをオーバーライドして、ブラウザが最初に接続するURL（エンドポイント）を設定する。

```java
@Override
public void registerStompEndpoints(StompEndpointRegistry registry) {
    registry.addEndpoint("/ws");
}
```

コードの役割は次のとおりである。

| コード | 役割 |
|--------|------|
| `@Override` | Springが用意したメソッドを実装する |
| `registerStompEndpoints()` | エンドポイントを設定するためのメソッド（Springが用意している） |
| `registry.addEndpoint("/ws")` | エンドポイントを`/ws`に設定する（`/ws`は開発者が決める） |

この設定により、ブラウザは`/ws`へ接続し、WebSocket通信を開始できる。

接続の流れは次のとおりである。

```text
ブラウザ
    │
    │ 接続要求
    ▼
/ws（エンドポイント）
    │
    ▼
サーバー
```

---

## 24. チャンネル設定

WebSocketでは、イベントを配信するためのチャンネルをあらかじめ設定する。

この設定は、Springが用意している`configureMessageBroker()`で行う。

```java
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.enableSimpleBroker("/topic");
}
```

コードの役割は次のとおりである。

| コード | 役割 |
|--------|------|
| `configureMessageBroker()` | チャンネルを設定するためのメソッド（Springが用意している） |
| `registry.enableSimpleBroker("/topic")` | `/topic`から始まるチャンネルを利用できるようにする |

例えば、`/topic`を設定すると、`/topic/questions`や`/topic/likes`などのチャンネルを利用できる。

## 25. トランザクションと配信タイミング

データベースの更新を伴うイベントは、トランザクションのコミットが成功した後に配信することが重要である。

例えば、質問投稿の処理中にエラーが発生した場合、データベースへの保存はロールバックされる。

```text
質問投稿
    │
    ▼
DBへ保存
    │
    ▼
エラー発生
    │
    ▼
ロールバック
```

一方、データベースのコミット前にイベントを配信すると、その後に処理が失敗した場合でも、配信済みのイベントは自動では取り消されない。

```text
DBへ保存
    │
    ▼
イベントを配信
    │
    ▼
エラー発生
    │
    ▼
DBはロールバック

画面：質問が追加されている
DB　：質問が保存されていない
```

そのため、画面とデータベースの状態を一致させるには、次の順番で処理する。

```text
DBへ保存
    │
    ▼
コミット成功
    │
    ▼
イベントを配信
    │
    ▼
画面を更新
```

Springでは、トランザクションのコミット後に処理を実行する`@TransactionalEventListener`などを利用して、コミット成功後にWebSocketイベントを配信する設計方法がある。

## 26. WebSocketとRedisの役割の違い

WebSocketとRedisは、どちらもリアルタイム通信で利用されることがあるが、役割は異なる。

| 技術 | 役割 |
|------|------|
| WebSocket | サーバーとブラウザの間でリアルタイムにデータを送受信する |
| Redis | サーバー間でデータを共有する |

例えば、Webアプリケーションサーバーが2台ある場合を考える。

```text
                 利用者
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   サーバーA                サーバーB
        │                       │
        └───────────┬───────────┘
                    ▼
                  Redis
```

WebSocketは、サーバーとブラウザの通信を担当する。

一方、Redisは、複数のサーバーから同じデータを参照できるようにする役割を持つ。

そのため、WebSocketとRedisは役割が競合する技術ではなく、それぞれ異なる目的で利用される。

live-qa-appでは、WebSocketでリアルタイム通信を行い、RedisはSpring Sessionの保存先として利用する設計である。

## 27. 受信後のUI更新

ブラウザは、チャンネルからイベントを受信すると、ペイロードを利用して画面の表示内容を更新する。

live-qa-appのフロントエンドではNext.jsを利用しているため、受信したデータをReactのState（画面に表示するデータを保持する仕組み）へ反映する。

例えば、質問投稿イベントを受信した場合の流れは次のとおりである。

```text
questionDto（ペイロード）を受信
        │
        ▼
質問一覧のStateを更新
        │
        ▼
Reactが画面を再描画
        │
        ▼
新しい質問を表示
```

Stateを更新する実装イメージは次のとおりである。

```javascript
setQuestions((currentQuestions) => [
    ...currentQuestions,
    questionDto
]);
```

コードの役割は次のとおりである。

| コード | 役割 |
|--------|------|
| `setQuestions()` | 質問一覧のStateを更新する |
| `currentQuestions` | 更新前の質問一覧 |
| `questionDto` | 新しく受信した質問のデータ |

`setQuestions()`によってStateが更新されると、Reactは変更を検知して画面を再描画する。

そのため、利用者がブラウザを手動で更新しなくても、新しい質問を画面へ表示できる。

---

## 28. 人気順の再ソート

質問一覧は、受信したイベントに応じて表示順を変更することもできる。

例えば、質問へ「いいね」が付いた場合は、更新された質問のいいね数をもとに人気順へ並び替える。

処理の流れは次のとおりである。

```text
いいねイベントを受信
        │
        ▼
questionDto（ペイロード）を受信
        │
        ▼
質問一覧のStateを更新
        │
        ▼
いいね数で再ソート
        │
        ▼
Reactが画面を再描画
```

そのため、利用者がブラウザを更新しなくても、質問一覧は人気順へ自動で並び替わる。

このように、WebSocketはデータの追加だけでなく、リアルタイムな画面更新にも利用できる。

## 29. WebSocketでCSRFをどう考えるか

WebSocketは、最初にHTTP通信（ハンドシェイク）で接続を開始する。

そのため、HTTP通信と同様に、CSRF（Cross-Site Request Forgery：利用者が意図しないリクエストを送信させられる攻撃）への対策を考える必要がある。

Spring Securityでは、接続時の認証やOrigin（どのWebサイトから接続してきたか）の確認により、不正なWebSocket接続を防ぐことができる。

# まとめ

WebSocketを利用すると、ブラウザとサーバーが接続を維持したままリアルタイムにデータを送受信できる。

live-qa-appでは、質問投稿やいいねなどのイベントをチャンネルへ配信し、接続中の参加者へリアルタイムに画面更新を通知する。

Spring Bootでは、`WebSocketConfig`でWebSocketを設定し、`SimpMessagingTemplate`でイベントを配信する。

ブラウザはチャンネルをSubscribe（購読）し、受信したペイロードをReactのStateへ反映することで、画面をリアルタイムに更新する。

また、認証・認可やSESSION Cookie、Redisを組み合わせることで、安全かつ複数サーバー環境にも対応したリアルタイム通信を実現できる。
