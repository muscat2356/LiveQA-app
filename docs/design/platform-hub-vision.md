# 将来構想: 母体アプリ（プラットフォーム・ハブ）と配下サービス

> **位置づけ**: ポートフォリオ期間（live-qa-app の MVP-A/B）の**対象外・将来ビジョン**。  
> いまの実装の正は [scope.md](../scope.md) / [architecture.md](../architecture.md)。本ドキュメントは「次の次」のプロダクト境界のメモ。

## 一言でいうと

**楽天アプリが母体、その下に楽天でんき・楽天モバイルがある**イメージで、

- **母体アプリ** … アカウント・SSO・横断のユーザー管理（退会・無効化・監査）の入り口  
- **配下アプリ** … LibraShare（蔵書共有など）／ live-qa-app（ライブQ&A）など、業務ごとのプロダクト  

という形を将来のゴールとする。

```text
        ┌─────────────────────────────────────┐
        │  母体アプリ（プラットフォーム・ハブ）      │
        │  ・ログイン / アカウント設定               │
        │  ・ユーザー管理（無効化・退会・監査）      │
        │  ・配下サービスへの導線・権限の見える化     │
        └───────────────┬─────────────────────┘
                        │ 同じ IdP（Keycloak realm）に相乗り
           ┌────────────┴────────────┐
           ▼                         ▼
   ┌───────────────┐         ┌───────────────┐
   │  LibraShare   │         │  live-qa-app  │
   │  （既存）      │         │  （本リポ）    │
   │  蔵書・貸出等  │         │  ライブQ&A    │
   └───────────────┘         └───────────────┘
```

楽天アナロジーとの対応:

| アナロジー | 本構想 |
|------------|--------|
| 楽天（母体） | 母体アプリ＝アカウントと横断管理のハブ |
| 楽天でんき / モバイル | LibraShare / live-qa-app など配下プロダクト |
| 楽天 ID | Keycloak 上の同一ユーザー（同一 realm の `sub`） |
| 各サービス固有データ | 各アプリの DB（蔵書、イベント Q&A など） |

## いま（MVP）との関係

| | いま（live-qa-app MVP） | 将来（母体構想） |
|--|------------------------|------------------|
| IdP | Keycloak・realm `LibraShare` に **client として相乗り** | 同じ IdP を母体が正面に出し、配下は第三者クライアントのまま |
| ユーザー行 | 各アプリが JIT でローカル `users`（FK 用の橋） | 無効化・退会の**業務の正**は母体。配下は必要なら反映用フラグ |
| ユーザー管理 UI | 無し（スコープ外） | 母体アプリに集約 |
| live-qa の削除カラム | **入れない**（[qa/java.md](../qa/java.md)） | 母体の方針が固まってから、配下へ Flyway で後付け可 |

**重要**: 母体が無い今でも、[qa/ops.md](../qa/ops.md) の「同じ realm に複数 client」は、この将来像の**下準備**になっている。

## 責務の分け方（案）

### 母体アプリが持つもの

- アカウントの見た目の「家」（プロフィール編集の導線、ログアウト、連携サービス一覧）
- **ユーザー管理**（管理者向け）: 無効化・退会・監査ログ、どの配下アプリを使えるか
- IdP（Keycloak）運用の窓口、または IdP の Admin API を呼ぶ BFF
- 配下アプリへのディープリンク / アプリスイッチャー

### 配下アプリ（LibraShare / live-qa）が持つもの

- そのドメインの業務データと API（蔵書、イベント、質問、投票…）
- ログインは母体／IdP に委譲（自前会員登録を増やさない）
- ローカル `users`（または同等）は **`oidc_subject` → ローカル PK** の橋＋所有者 FK
- 母体から「無効化された」通知／フラグを受けたら、新規操作を 403 にする、など**反映**

### Keycloak（IdP）が持つもの

- 認証の正（パスワード、SSO セッション、realm roles / client roles）
- アプリごとの client 登録（redirect URI、secret）
- 「ログインできるか」の最終ゲート（ユーザー disable など IdP ネイティブ機能も候補）

母体は「Keycloak を置き換える」のではなく、**Keycloak の上に立つ運用・管理 UI / ポリシー層**、と捉えると衝突しにくい。

## データの流れ（将来・概念）

### ログイン（配下アプリ利用時）

```text
ユーザー → 母体 or 配下の「ログイン」
  → Keycloak（同一 realm）で認証
  → 配下 backend が oauth2Login → セッション発行
  → 配下 JIT: ローカル users を sub で検索／作成
  → 母体側で「無効」なら配下は 403（反映の仕組みは後述）
```

### 管理者による無効化（母体）

```text
管理者 → 母体のユーザー管理で「利用停止」
  → （A）Keycloak ユーザーを disable する
  → および／または（B）母体 DB に disabled_at を記録し、配下へ伝播
  → LibraShare / live-qa は以降ログイン拒否 or API 403
  → 各配下の業務データ（イベント履歴など）は原則残す（FK・監査のため）
```

伝播のやり方は未決でよい。候補だけ列挙する:

| 方式 | 概要 | 向き |
|------|------|------|
| IdP disable のみ | Keycloak で止め、配下はログイン不可 | 単純。配下ローカル行は孤児になりうる |
| 母体 API を配下が問い合わせ | リクエストごとに「有効か」を確認 | 結合が強い |
| イベント／Webhook | 無効化を配下が受けてローカル `disabled_at` を更新 | 疎結合。Flyway 後付けと相性が良い |
| 共有ユーザー DB | 母体と配下が同じ users 表を見る | 結合が強すぎるので初期は非推奨 |

## live-qa-app / LibraShare 側で今やっておくと効くこと

1. **同じ Keycloak realm への client 相乗りを維持する**（既に進行中）  
2. ローカル `users` を「プロフィールの正」にしない（クレームは都度、JIT は橋だけ）  
3. MVP で `deleted_at` を急がない。母体の無効化モデルが決まってから `disabled_at` 等を追加  
4. ロールは realm / client で整理する（例: live-qa の `HOST` は live-qa 用、LibraShare の社員ロールは別）  
5. 本ドキュメントを「将来の正の置き場」として更新し、実装は母体リポ新設時に落とす

## やらないこと（この構想でも）

- live-qa MVP 期間中に母体アプリ本体を実装すること  
- 配下アプリの業務 DB を母体に統合すること  
- 決済・ポイント・楽天生態系そのものの再現
