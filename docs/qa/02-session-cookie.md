# セッション / Cookie / SameSite

## セッションとは（このラボの意味）

**セッション** = 「このブラウザとの一連の会話を、サーバ側で覚えておく仕組み」。

ブラウザは毎回バラバラの HTTP リクエストを送る。サーバは本来「さっきの人」か分からない。そこで:

1. サーバが **箱（セッション）** を作る  
2. 箱の **鍵（ID）** だけを Cookie `SESSION` でブラウザに渡す（**発行**）  
3. 箱の中身は Redis に置く（**格納**）  
4. 次のリクエストで鍵を見て箱を読み戻す（**復元**）

「ログインした」ことや CSRF トークンなども、この箱の中に入る。

### 登場人物

| 名前 | 正体 | 役割 |
|------|------|------|
| セッション（中身） | サーバ側のデータの箱 | 誰か・権限・一時データ |
| セッション ID | 文字列（UUID など） | 箱の鍵 |
| `SESSION` Cookie | ブラウザが送る鍵 | HttpOnly。JS からは読めない |
| Redis | 箱の倉庫 | アプリ再起動しても残せる |
| Spring Session | ライブラリ | HttpSession の実体を Redis に載せる |
| `SecurityContext` | Security の「今の認証情報」 | ログイン後に箱へ入る本丸 |

よくある誤解: Cookie にユーザー名が入っている → **入っていない**。入っているのは ID だけ。

### データの流れ

```text
① 初回アクセス（またはログイン成功）
   → 格納: Redis に spring:session:sessions:{ID}
   → 発行: Set-Cookie: SESSION={ID}; HttpOnly; SameSite=Lax

② 2回目以降
   ブラウザが Cookie: SESSION={ID} を付ける
   → 復元: Redis から箱を読む

③ ログアウト / TTL 切れ
   → 箱を消す or 期限切れ
```

| 操作 | 意味 |
|------|------|
| **発行** | 鍵（ID）を Cookie でブラウザに渡す |
| **格納** | 箱の中身を Redis に書く |
| **復元** | 鍵で Redis から箱を読み戻す |
| **破棄** | ログアウト等で箱を消す |

### 「URL を開いただけ」と「ログイン後」

| | アクセスしただけ | Keycloak ログイン後 |
|--|------------------|---------------------|
| 箱 | ある（CSRF・戻り先など） | ある |
| 中の本人情報 | ほぼ無し／匿名 | `SecurityContext`（ユーザー・ロール） |
| `/api/me` | 401 想定 | 200 想定 |

セッションがある ≠ ログイン済み。  
**ログイン済み = 箱の中に認証情報が入っている**。

### なぜ Cookie セッションか

```text
入口だけ Keycloak（OIDC）
  → 交換 → 変換 → 格納
  → 以降は SESSION Cookie だけ（JWT を毎回検証しない）
```

| 方式 | イメージ |
|------|----------|
| JWT 毎回検証（LibraShare 寄り） | リクエストごとにトークンを確かめる |
| Cookie セッション（このラボ／本番） | 一度橋渡ししたら、鍵だけで箱を復元 |

## Cookie はクライアント側にあるものでは？

**そのとおり。Cookie はクライアント（ブラウザ）側に保存される。**

| どこ | 何があるか |
|------|------------|
| **ブラウザ（クライアント）** | Cookie。例: `SESSION=abc-123`（鍵だけ） |
| **サーバ / Redis** | セッションの箱（中身） |

```text
ブラウザが持つもの … Cookie（鍵）
サーバが持つもの   … セッション（箱）
```

正しくは:

> **セッション ID を Cookie に載せてブラウザに渡す（発行）**  
> **中身はサーバ側（このラボでは Redis）に格納する**

リクエストのたび:

1. ブラウザが自分の Cookie をリクエストに付ける  
2. サーバが `SESSION` の値（ID）を読む  
3. Redis から箱を **復元** する  

`SESSION` に HttpOnly が付いていると、**JS からは読めないが、ブラウザは自動でリクエストに付ける**。  
置き場所はクライアント、ページのスクリプトからは隠している。

## SameSite とは？データの流れは？

**SameSite** は Cookie の属性で、「**別サイトからのリクエストに、この Cookie を付けるかどうか**」をブラウザに指示する。

| 値 | 意味 | ラボでの扱い |
|----|------|----------------|
| `Strict` | 自分のサイト内の遷移だけで送る | 厳しすぎて戻りで困ることがある |
| `Lax`（ラボ推奨） | 普通のリンクで自サイトに来る GET では送る。他サイト起点の POST などでは送らない | CSRF と利便性のバランス |
| `None` | クロスサイトでも送る（必ず `Secure`） | ラボでは使わない |

`serializer.setSameSite("Lax")` は、**発行**する `SESSION` Cookie に「Lax で扱え」と印を付ける、という意味。

### SameSite が効く流れ

```text
① ログイン成功（またはセッション作成）
   API → ブラウザ
   Set-Cookie: SESSION=...; HttpOnly; SameSite=Lax
   （発行）

② 同じサイト内で API を叩く
   ブラウザ → API
   Cookie: SESSION=...
   （復元 → Redis から読み戻す）
   ※ 同一サイトなので送られる

③ 悪意ある別サイトがクロスサイト POST を踏ませる
   → SameSite=Lax だと SESSION が付かないことが多い
   → 勝手な操作が通しにくい
```

ポイント:

- SameSite は **Redis の中身を変えない**。効くのは「ブラウザが Cookie を付けるか」
- CSRF 対策の本命は **`XSRF-TOKEN` + `X-XSRF-TOKEN` の検証**。SameSite は補強
- `SessionConfig` の `DefaultCookieSerializer`（実装クラス）が名前・SameSite・HttpOnly を実際にセットする

## なぜ URL アクセスしただけで Session が発行される？

ログインしていなくてもセッションが付くのは、**「ログイン＝セッション」ではなく「HTTP を扱う都合でセッションが必要になる」**ことがあるから。

### 結論

URL にアクセスした時点で、Spring Security（と Spring Session）が  
**CSRF 用トークン**や**ログイン前の戻り先**などを置く箱としてセッションを作り、  
その ID を `SESSION` Cookie として **発行**している。  
中身は「主催者としてログイン済み」とは限らない（匿名／未認証の箱）。

### 流れ

```text
ブラウザ → GET http://localhost:8080/
        → Spring Security のフィルタが動く
        → 必要なら HttpSession を作る
        → Spring Session が Redis に格納
        → Set-Cookie: SESSION=... を発行
```

### なぜ「必要」と判断されるか

`SecurityConfig` が空のあいだは **Spring Boot のデフォルト Security** が効く。

1. **CSRF** … デフォルト有効。セッションを作りがち  
2. **保護された URL** … ログインへ飛ばす前に戻り先をセッションに格納することがある  
3. **SessionCreationPolicy** … だいたい「必要なら作る」（`IF_REQUIRED`）  
4. **oauth2-client が classpath にある** … state などをセッションに載せることがある  

「URL を開いただけ」＝「HOST として認証された」ではない。

## 別サーバに Redis を立てると Tomcat セッションと違いメモリを使わず箱を保持できる？

**だいたいその認識で合っている。** 一点だけ言い換えると正確。

### 合っているところ

**アプリ（Tomcat / Spring Boot の JVM）のヒープにセッション箱を置き続けない**、という理解は正しい。

| | Tomcat 標準セッション | Spring Session + Redis |
|--|----------------------|-------------------------|
| 箱の置き場 | そのサーバのメモリ（JVM） | Redis（別プロセス／別サーバ可） |
| アプリ再起動 | 箱が消えやすい | Redis が生きていれば残せる |
| アプリを複数台 | 共有しにくい | 同じ Redis を見れば Cookie 一本で共有しやすい |

別サーバに Redis = **箱の倉庫をアプリの外に出す**。

### 補足

Redis も基本は **メモリ上のストア**。「メモリを使わない」のではなく:

- **使わない** → アプリ JVM のメモリ（セッション分）  
- **使う** → Redis サーバ側のメモリ  

一文:

> Tomcat セッションは「そのアプリのメモリが箱」。Redis セッションは「別プロセス（別サーバ可）の倉庫が箱で、アプリは鍵（Cookie）だけ持つ」。
